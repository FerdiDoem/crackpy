Architecture Shift

The important change is locality: Williams-specific fitting, parameters, typed results, provenance source construction, envelope building, and YAML definitions now live with the Williams method module.

Before

1
Mutable FractureAnalysis state
Williams results and coefficients were extracted from broad analysis attributes.
2
Result-side Williams adapter
Method knowledge sat in result/provenance infrastructure.
3
Harder method extension path
Future CJP or J-integral slices risked copying Williams details into shared result code.

After

1
run_williams_fit()
Numerical execution lives in the method module and returns typed results.
2
source_from_result()
Typed result plus typed parameters become a minimal MethodResultSource.
3
Canonical envelope and projections
Existing JSON, compact KG, and graph visualization behavior stay attached to stable records.

Design Decisions Preserved

Minimal source snapshot

MethodResultSource stays a value object with inputs, dependencies, parameters, and quantities. Method-specific concepts remain in method modules or quantity qualifiers.

Definitions separate from logic

spec.yaml owns stable schema strings, quantity aliases, dependency roles, and method metadata. Python keeps numerical work, extraction, validation, and envelope building.

Transition facade

crackpy.results.williams_provenance keeps current imports working while Williams-specific implementation moves under fracture_analysis.methods.williams_fit.

Follow-up Watchpoints

Items worth checking before this pattern is reused for another method family.

Analysis facade shrinkage

FractureAnalysis still adapts legacy attributes. The next slices should avoid adding more extraction logic there.

Spec validation pressure

If qualifiers grow beyond Williams coefficients, validate allowed qualifier keys through specs before expanding MethodResultSource.

Method module pattern

CJP and J-integral should prove the same vertical shape before adding a registry or broader method abstraction.
