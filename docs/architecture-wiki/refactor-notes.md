## Inspection Prototypes

### CrackPy Lab Frontend Prototype

Status: inspection artifact, not approved product architecture

Location: `docs/inspection/crackpy-lab-prototype/`

Purpose: demonstrate a possible scientific workbench for starting CrackPy-style experiments, inspecting crack-tip correction and fracture-analysis outputs, and showing result provenance without changing production package boundaries.

Data policy: the prototype data file is generated by `docs/inspection/crackpy-lab-prototype/build_data.py` from current repository fixtures, including `test_data/fracture_analysis/results_auto_integral_probs.csv`, `test_data/fracture_analysis/txt-files/`, `test_data/crack_info_by_nodemap.txt`, `test_data/crack_detection/Nodemaps/`, and the Williams provenance graph JSON under `.scratch/williams-export-proof/` when present. The browser still uses a static `data.js` artifact, but its numeric result rows are not hand-authored mock data.

Prototype data fields:

- `experimentPresets`: UI presets for specimen, loading, and DIC acquisition context; exists so the prototype can switch between realistic experiment families without importing CrackPy runtime code.
- `analysisMethods`: method labels, source descriptions, output labels, and units; exists to keep K, J, Williams, CJP, interaction-integral, and Bueckner-Chen values visibly tied to their estimator/source.
- `resultFrames`: deterministic frame-level crack-tip estimates, corrected crack-tip estimates, correction deltas, metrics, warnings, and provenance step IDs; exists to demonstrate result inspection and frame selection.
- `provenanceSteps`: ordered source/result processing descriptions; exists to preview how a method-result envelope could be explained in UI.
- `warnings`: scientific caution messages keyed by frame; exists to avoid presenting experimental or source-sensitive results as unqualified truth.
- `tableRows`: flattened method/result rows; exists as a result-table demonstrator and should not be treated as the current CrackPy result schema.
- `visualizationConfig.nodemapBaseLayer`: permanent nodemap visualization base generated from an actual nodemap fixture, including point-level `x`, `y`, `eps_eqv`, `disp_y`, and `eps_xy` values plus field statistics; exists so the prototype renders a live nodemap canvas with colormap, `vmin`/`vmax`, and sigma-based scaling controls rather than relying only on static PNG assets.
- `visualizationConfig.lineIntegralDefaults`: UI-facing copy of line-integral path defaults such as `number_of_paths`, `integral_tick_size_mm`, `number_of_nodes`, `mask_tolerance`, and `buckner_williams_terms`; exists to show current CrackPy configuration vocabulary without defining a new schema.
- `visualizationConfig.crackDetectionDefaults`: UI-facing crack-tip detection window defaults such as window size, input resolution, and angle-detection radius; exists so the setup view can draw only the detection region geometry over the nodemap.
- `visualizationConfig.williamsDefaults`: UI-facing Williams setup configuration including radius bounds, angle gap, tick size, and terms; exists to draw the fit annulus only, not to imply that the prototype can reconstruct individual Williams fields.
- `actualDataSources`: repository-relative source paths used to generate the current `data.js`; exists so reviewers can distinguish fixture-backed results from UI-only demonstrator state.
- `actualGraphSummary`: counts, source path, and scope note from a separate exported Williams proof graph JSON; exists so the UI can show provenance graph node classes without pretending this graph belongs to the currently selected Dummy2 frame.
- `graphNodeTypes`: frontend-facing provenance graph node labels derived from the current graph visualization artifact; exists to expose candidate UI nodes such as `InputRecord`, `CrackTipFrame`, `AnalysisRun`, and `ResultQuantity`.
- `graphEdges`: type-level graph edges derived from the actual exported graph JSON; exists to visualize how frontend-facing node classes connect without shipping every individual quantity node as a separate control.

Boundary: this prototype intentionally uses static browser data and does not define a new CrackPy API, service layer, schema, package dependency, or approved refactor target. Any production frontend or result API should be specified separately before implementation.
